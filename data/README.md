# Data

Two things live here, and they are unrelated:

1. **Runtime data contract** — the structures the app and benches actually read. Small, tracked.
2. **Contact prior versioning (I86)** — `4W52_contacts.json`. Unchanged by S5.

# 1. Runtime data contract (S5)

## What the app needs at runtime

| What | Path | Why |
|---|---|---|
| Demo protein (`4W52` = T4L + benzene) | `4w52.pdb` (repo root, 151 KiB) | `src/pdb.js:fetchPdb()` probes `./<id>.pdb` then `./data/<id>.pdb`; the 1-click sample button resolves `4W52` → `./4w52.pdb` |
| Demo ligands | `1crn.pdb`, `1ubq.pdb` (repo root) | apo controls used by benches and tests |
| Extra structure | `4hhb.pdb`, `1ake.pdb` (repo root) | 4HHB multi-chain + larger-system tests |
| Ligand MOL2 | `benzene.mol2` (repo root, 1.2 KiB) | reference ligand for tests/benches |
| Any other structure | *nothing tracked* | user file-picker, or RCSB/PDBe download at runtime |
| User ligand MOL2 | *nothing tracked* | `index.html:#mol2File` file input only |

**The app has no code path that reads a ligand MOL2 by name, and no code path that
can reach `data/coreset/<id>/<id>_protein.pdb`.** `fetchPdb()` takes a bare
4-character PDB ID and probes flat paths; a `data/coreset/1a30/1a30_protein.pdb`
layout is structurally unreachable. The 4W52 demo takes its BNZ ligand from the
`HETATM` records inside `4w52.pdb` itself, not from a MOL2 file.

## What is bench-only

**Nothing in `data/coreset/` is bench-only, because no bench reads it.** Measured

## Why is it untracked? (provenance)

The files are **commercial-tool exports, not raw upstream downloads.** The PDB
headers say so themselves:

| File | Self-declared origin |
|---|---|
| `<id>_protein.pdb` | `REMARK  GENERATED BY SYBYL (TRIPOS, INC.)  12-MAR-16` |
| `<id>_pocket.pdb` | `REMARK  GENERATED BY X-TOOL on Mon Nov 18 12:27:08 2013` |
| `<id>_ligand.sdf` | `Created by X-TOOL on Fri Sep 26 17:34:14 2014` |
| `<id>_ligand.mol2` | SYBYL export, 2018 |
| `<id>_ligand_opt.mol2` | same molecule 2 minutes later, optimized coordinates |
| `<id>_protein.mol2` | SYBYL export, 2016 |

Because of this there is **no byte-exact public mirror**, and a downloader that
"reconstructed" these from RCSB or a bare PDBbind tarball would produce
*different bytes* while looking perfectly plausible. `scripts/fetch_coreset.mjs`
therefore never fabricates a substitute: bytes are only written into
`data/coreset/` if they match the SHA256 in `data/manifest.json`.

Also measured: `<id>_ligand_opt.mol2` differs from `<id>_ligand.mol2` **only** in
coordinates and the two SYBYL timestamp lines — i.e. it is a pure derivative, and
`<id>_protein.mol2` (233.92 MiB, 59% of the tree) is a MOL2 re-encoding of a file
the app already has in a form it can read.

## How to restore

```bash
# 1. verify what you have (default mode — no network, no writes)
node scripts/fetch_coreset.mjs

# 2. restore byte-exactly from an extracted PDBbind/SYBYL export tree
node scripts/fetch_coreset.mjs --restore-from /path/to/extracted/tree

# 3. inventory and per-kind sizes
node scripts/fetch_coreset.mjs --list
```

`--restore-from` SHA256-verifies every file and **skips** (never installs) any file
whose hash does not match, so a partial or wrong restore fails loudly instead of
leaving a plausible-looking wrong file on disk. It accepts either
`<dir>/coreset/<id>/<file>` or `<dir>/<id>/<file>`.

`--fetch --base-url https://…` exists for an explicit opt-in network restore, but
expect most downloads to be **rejected on hash mismatch** — that is the script
working correctly, given the provenance above.

If you add a bench that genuinely needs the coreset:

```bash
git add -f data/coreset        # re-track
```

## Benches fail loudly instead of mis-measuring

`bench/require_inputs.js` makes both benches resolve their **entire declared input
set** before printing any number, and SHA256-check it against
`data/manifest.json`. Missing input → exit 1, no metric. Corrupt input → exit 1,
no metric.

This fixed a real defect. Previously, hiding `1ubq.pdb` made
`bench/pdbbind_gb.js` swallow the error, average over the surviving 2 of 3 targets,
print `PASS: RMSE <2.5 kcal/mol`, and **exit 0** — with RMSE *improving* from
1.53 to 0.96 purely because the worst target had disappeared. That is precisely
the "overselling a broken run" failure mode called out in `ROADMAP.md` section 1.
Per-target compute failures are now also fatal (`requireAllTargetsComputed`).

## `data/manifest.json`

- `version` — manifest format version.
- `4w52.pdb` — SHA256 of the demo structure the app and benches depend on.
  Verified still valid; `bench/require_inputs.js` enforces it at bench startup.
- `coreset.files` — SHA256 of all 1712 untracked files (~192 KiB of JSON, 0.05%
  of what it replaces), so the restore path is verifiable rather than hopeful.

# 2. Contact Prior Versioning (I86)

## 4W52_contacts.json header

`data/4W52_contacts.json` ships a **versioned contact prior** for the Elastic Network Model scaling `γ·(1+α·p_ij)` (see `src/ml-tier.js`, `ml/export_esm_contacts.py`).

Header fields:

```json
{
  "source": "heuristic",
  "chain": "A",
  "sequence": "MNIFEM...KNL",
  "nRes": 164,
  "meta": {
    "created": "2026-08-05T15:22:25.947030+00:00",
    "min_p": 0.05,
    "model_version": "heuristic-v1",
    "version": "1.0.0",
    "model": "heuristic",
    "contact_prior_version": "1.0.0-heuristic-v1"
  },
  "contacts": [[i, j, p_ij], ...]
}
```

- `source` — ML source (`heuristic` or ESM model e.g. `esm2_t33_650M_UR50D` when `ml/export_esm_contacts.py --model` is used)
- `model_version` — **contact prior version** (`heuristic-v1` for the checked-in file; ESM mode writes `esm2_t33_650M_UR50D-v1`)
- `version` — semantic file format version (`1.0.0`)
- `contact_prior_version` — combined `version-model_version` for provenance (`1.0.0-heuristic-v1`)
- `min_p` — threshold that filtered `contacts` (`0.05`)
- `created` — ISO8601 creation timestamp

## Versioning policy

- **heuristic-v1** — deterministic Kyte-Doolittle + Gaussian pseudo-prior (no ESM weights). Ships with repo; `ml/export_esm_contacts.py` produces it when `fair-esm` is absent (`[esm unavailable - using heuristic prior]`).
- **esm2_t6_8M_UR50D-v1**, **esm2_t33_650M_UR50D-v1**, etc. — real ESM-derived attention prior from `ml/export_esm_contacts.py --model <name>`.

Bumping `version` (e.g. `1.0.1`, `2.0.0`) signals a breaking change in `contacts` format; bumping `model_version` signals new weights/thresholds.

## Generating a new versioned prior

```bash
# heuristic-v1 (no ESM)
python3 ml/export_esm_contacts.py --pdb 4w52.pdb --out data/4W52_contacts.json --min-p 0.05

# ESM mode (requires fair-esm + torch)
pip install fair-esm torch
python3 ml/export_esm_contacts.py --pdb 4w52.pdb --out contacts.json --model esm2_t6_8M_UR50D --min-p 0.05
# -> source=esm2_t6_8M_UR50D, model_version=esm2_t6_8M_UR50D-v1
```

The exporter writes `meta.model_version` and `meta.version` automatically; older files without a `model_version` should be re-exported or manually annotated.
