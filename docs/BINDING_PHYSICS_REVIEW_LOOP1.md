## 3. Discrepancies found (all minor; none blocks Loop 2)

- **D1 — `renderPmfFormation` is not null-bindlog-safe** (real bug, one line):
  `bindviz.js:222` dereferences `bindlog.nEvents` without a null guard; my re-test
  shows `renderPmfFormation(canvas, null)` throws, while timeline/energy renderers
  handle null correctly. R7 §1's blanket claim ("null canvas / empty BindLog → …
  never throw") is *tested* only for null canvas + **empty** BindLog, both of which
  pass. Fix in Loop-2 S6: add `if (!bindlog) return drawEmpty(...)`.
- **D2 — R2 microbench internal inconsistency:** doc §2a/§3 report 21.1 vs 15.7
  ns/pair (**1.3×**); my re-run measured 21.56 vs 14.15 = **1.5×**, and the prototype
  itself prints 1.5× in §F but 1.3× in its SUMMARY. Machine/session variance plus
  sloppy summary. The <5% frame-impact conclusion is unaffected (flagged pairs ≪ 1%
  of cross pairs) but Loop-2 S2 should budget against the conservative 1.5×.
- **D3 — R4 prototype stale banner:** prints "(holo **2000** steps BAOAB-lite)" while
  the code (and the doc, correctly) runs **6000** steps. Cosmetic only.
- **D4 — benchmark session variance + CSV regeneration:** `pareto_bench.mjs` rewrites
  `docs/pareto_frontier.csv` by design; my sanctioned `--quick` re-run replaced the
  committed numbers (L0 0.313 vs 0.203, L2 86.6 vs 82.5, heap 16.1 vs 9.1 MB).
  Quick mode uses N=200/20 steps (vs 1000/100 full) → noisier timings and heap
  snapshot drift. Not an error, but **Loop-2 S7 must re-run in full mode** before
  publishing tier numbers, and the heap column should be read as ±50%.
- **D5 — R6 "10k events = 800 KB" attribution:** 800 KB is the amortized capacity at
  27,136 events (energy pushes are 7-component); 10k single events would be ~400 KB.
  Direction of the claim (typed arrays ≪ per-event objects) is right; wording imprecise.
- **D6 — R1 §0 heavy epsHB range nit:** doc says "epsHB = 2.5–3.0"; `hbond.js` header
  says "2.0 to 4.0" with default 3.0. Default is inside both ranges; nit only.
- **D7 — R2 §7 note on pre-existing dirty tree confirmed:** `git status` shows
  `main.js/ml-tier.js/network-panel.js/settings-panel/css` modified — these pre-date
  the binding program (consistent with the doc's claim that R2 touched no physics;
  verified `ff-binding.js`/`ff-params.js`/`forcefield.js` are clean vs HEAD).

## 5. Top 3 risks for Loop 2

1. **Hot-path regression in S2** (the only step that edits the per-pair CG loop):
   directional cost measured 1.3–1.5× on the flagged subset plus O(nProt) frame
   rebuild each force call. Mitigation: budget 1.5× (D2), β tables precomputed,
   sites rebuilt once per force call not per pair; pareto_bench CG gate (<0.5 ms/step)
   after the change; stopgap flag fix held in reserve.
2. **Silent double-counting in S3** (aromatic LJ ε-downscale too weak/strong, or
   cation-π charge gating omitted): would distort exactly the rankings the term is
   meant to improve. Mitigation: S4 per-term accumulators land adjacent in sequence —
   diff per-term energies before/after S3 to expose any double-count; R3 prototype
   geometries become permanent unit tests.
3. **DOM-contract regression in S6** (Phase-5 history: three incidents): the deferral
   was correct but the risk transfers to Loop 2. Mitigation: P5 gate (before/after
   screenshots), collapsed `<details>` default, wikiskill DOM-contract gate as hard
   prerequisite, ≤1 Hz render cadence to protect frame budget.
